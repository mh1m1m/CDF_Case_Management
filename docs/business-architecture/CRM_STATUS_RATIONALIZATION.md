# CRM Status Rationalization «ترشيد حالات التذكرة»

- **Status:** Every legacy status in both status catalogues, and every `CDF_CASE_V1` state, is mapped and grounded in the implemented schema: each target is a value the database stores today, an audit event a command emits today, or is marked PLANNED (migration 1970, `config.legacy_status_map`, ADR-035).
- **Sources:**
  - the owner's Drive document "Whistleblowing & Behavioral Misconduct CRM Case Management System" (§8 «توثيق الحالة»), read 2026-10-12: **150** statuses, S001–S150. It is a _proposed_ catalogue (owner answer G1: «catalogue مقترح/مصمم داخليًا»), ranked 8th in the playbook's source hierarchy;
  - the owner's **140**-status list supplied with the 274-item control catalogue on 2026-10-12 ([The 140-status catalogue](#the-140-status-catalogue)). The rebase prompt's "140 statuses" is this list.
- **Conflict between the two catalogues (surfaced, not resolved).** 127 codes carry the same status in both lists. S024, S029 and S122 are worded differently with the same meaning. **S021–S023, S025–S028, S030, S099 and S100 mean different things** (for example S099 is «قياس الأثر بعد التنفيذ» in the 150 list and «تجميد قانوني» in the 140 list). Most of the 140-list names for these codes (for example «تعليق التحقيق – تغيير محقق» and «بانتظار تشكيل لجنة تحقيق») also appear in the Drive document's own §9 transition table, while most §8 names for them do not, so the §8 list may be the outlier. Both readings are kept, keyed by (catalogue, code), and a legacy value is never resolved by its code alone. Which list is authoritative is SOURCE_REQUIRED.
- **Also known as:** `STATUS_CATALOGUE_RATIONALIZATION.md` in the rebase prompt.
- **Rule (playbook §7–§10):** no single case-status enum. Each legacy label maps to exactly one semantic type and one target. Display strings such as «قيد التحقيق — بانتظار الرأي القانوني» are _derived_ from structured state, never stored as the truth (DEC-34).
- **Nothing is silently deleted.** OBSOLETE, DUPLICATE and RETIRE rows keep their code so reporting and the continuity import can map legacy values (`config.legacy_status_map`).

## Target dimensions

Kinds: **STORED** is a check-constrained column, and its values here equal the constraint exactly. **STATUS_CODE** values are `config.status_code` rows, which `case_mgmt.require_status_code` enforces. **DERIVED** values are computed from stored state and are not built yet. **PLANNED** dimensions are not modelled. A test keeps this table, the constraints and `config.status_dimension_value` equal.

## Reading this table

- **EVENT** rows become audit actions and timeline entries on the object named in _Notes_ (meeting, evidence, mandate, notice). They are not states, so the case never "sits" in them.
- **REPLACE** means a domain object now carries the concept (for example S021 «جلسة استماع» is a `committee.meeting` with purpose HEARING; S034 «بانتظار تشكيل لجنة» is retired because committees are permanent, Q21).
- **Grounding changed some design targets.** For example S006's INVESTIGATING is the implemented proceeding status IN_PROGRESS; S016 (escalated) is the approved preliminary recommendation REFERRED_TO_COMMITTEE; S046 (conflicting committee opinions) is the vote result TIED that the casting vote settles (Q57); S095 (authority conflict) is the authority outcome RETURN_TO_COMMITTEE.
- **SOURCE_REQUIRED** values (who may order an emergency closure, board-referral authority, binding legal opinions, internal settlement basis, quality reviewer role) stay configurable reference data until a CDF source exists (playbook §106).
- **Gaps** found while grounding are listed in [FORM_CATALOGUE_RATIONALIZATION.md](FORM_CATALOGUE_RATIONALIZATION.md) §6 (P11-G1 … P11-G7).
