# ADR-034: Continuity workbook template BCP-1 and the governed import pipeline

- **Status:** Proposed (2026-10-12). Linear CDF-197. Implemented in migration 1960 (local, pending security review). Security-sensitive.
- **Protocol:** §12, §19, §29, §45, §68, §82–§83, §87; ADR-027, ADR-021, ADR-023, ADR-024, ADR-033; owner Q&A Q100.

## Context

ADR-027 decides that a full outage is run from a governed Excel workbook and that its records come back through validation, a difference review, approval by a separate user and a transactional import through the same commands, with the offline provenance kept (Q100). It leaves open the template's exact shape, how a workbook is read safely, how rows map to commands, what a conflict is, who approves, and how the original event time survives an import that runs through commands which stamp their own time.

## Decision

1. **One versioned template, BCP-1.** The template is defined once, in `@cdf/contracts` (`BCP_TEMPLATE`), and seeded as reference data (`exchange.bcp_template_column`); a test keeps the two equal. It has the 27 sheets of the owner's list, 00_README to 26_IMPORT_AUDIT. Row 1 of a data sheet holds the column codes, row 2 their labels, and data starts on row 3. Every data row carries `ROW_ID` (a stable `BCP-` key or a UUID; never the Excel row number), `OBJECT_ID` (the platform object the row is about, if any), `ORIGINAL_EVENT_AT` and `RECORDED_OFFLINE_BY`. 01_CONTROL names the template version, the workbook id, the case (id and number, both required), the offline window and who prepared it. The empty template ships as `infrastructure/bcp/BCP-1_template.xlsx`, generated by `buildBcpTemplate` from that definition with bilingual column labels from `@cdf/i18n` (every cell formatted as text, header rows frozen); a unit test keeps the committed file byte-identical to the generator's output. Synthetic saves of it by openpyxl and LibreOffice Calc are reader test fixtures.
2. **BCP-1 imports four sheets of a case workbook; the others are recorded, not imported.** 05_SUBJECTS (`api.add_case_subject`), 06_ALLEGATIONS (`api.add_allegation`), 18_EMPLOYEE_NOTICE (a defence response received on paper, `api.record_defence_response`) and 21_CORRECTIVE_ACTIONS (`api.open_corrective_action`). Rows on every other sheet are staged as UNSUPPORTED and must be skipped explicitly; they are entered online after restoration. A case workbook belongs to the case team, who see the case. The committee's offline work (meetings, attendance, conflicts, votes, minutes and the authority decision the secretary records, CDF-159) needs a workbook scoped to a committee proceeding, because the secretary does not see the case (DEC-02, ADR-031); grievances need one scoped to the Grievance Committee. Those, documents and evidence (a companion package, after UX S2), status history and a pre-filled check-out workbook are the next increment.
3. **The workbook is untrusted input, read without a new dependency.** The reader (`readWorkbook` in `@cdf/infrastructure`, behind the `WorkbookReader` port) uses `node:zlib` only. It checks the compressed size, the entry count and every entry's declared size before inflating anything, inflates with a hard output limit, refuses encrypted, ZIP64, unknown-method, duplicate, absolute and `..` entries, and parses only the workbook, its relationships, the shared strings and the worksheets those name. It refuses any DTD or entity declaration, decodes only the predefined and numeric character references, and returns every cell as a string, flagging formula cells. It covers the subset of SpreadsheetML that the BCP-1 template and Excel or LibreOffice saves of it use; anything else is refused (PRODUCTION_SUBSTITUTION_REQUIRED: a vetted reader in the CDF runtime). The upload is scanned by the `MalwareScanner` port first, and only a CLEAN result is read. Caps (`BCP_WORKBOOK_LIMITS`): a 10 MiB file (`BCP_MAX_WORKBOOK_BYTES`, also checked by the application before the scan), 200 entries, 64 MiB per inflated entry, 128 MiB inflated in total, a compression ratio of 500, 40 sheets, 2 100 rows, 67 200 cells and 32 columns per sheet, 20 000 characters per cell, 268 800 shared strings and an XML nesting depth of 64. A refusal is a stable code with no file content: from the container NOT_A_ZIP, TOO_LARGE, MULTI_DISK, ZIP64, TOO_MANY_ENTRIES, ENCRYPTED, UNSUPPORTED_METHOD, UNSAFE_PATH, DUPLICATE_ENTRY, ENTRY_TOO_LARGE, TOTAL_TOO_LARGE, RATIO_TOO_HIGH, CORRUPT; from the XML DTD, ENTITY, MALFORMED, TOO_DEEP; from the workbook MACROS, EMBEDDED_CONTENT, EXTERNAL_LINK, NOT_A_WORKBOOK, UNSUPPORTED_SHEET, UNSUPPORTED_CELL, TOO_MANY_SHEETS, TOO_MANY_ROWS, TOO_MANY_CELLS, TOO_MANY_COLUMNS, CELL_TOO_LONG.
4. **Staging validates twice and classifies every row.** The application accepts only an `.xlsx` file uploaded from the case page its control row names (WORKBOOK_CASE_MISMATCH otherwise), checks the template (`readBcpWorkbook` in `@cdf/domain`: exactly the 27 sheets, row 1 the column codes from column A and typed, one typed control row on row 3, version BCP-1, no cells beyond a sheet's columns, at least one row) and validates the control row and rows with the same column rules as the database (`@cdf/validation`, §45; a database test keeps the two equal on every column kind); the database checks them again in `api.stage_bcp_import`. The importer (`BCP_IMPORT`) must see the case the control names (`NOT_FOUND` otherwise). Each row is NEW, CONFLICT (it names an existing object, or a row already imported from this workbook has changed), ALREADY_IMPORTED (no-op), UNSUPPORTED or INVALID (with the failing column). An event time must fall within the control's offline window, not before the case was created and not in the future; the offline recorder must be a platform user. One case and workbook id have at most one open batch.
5. **Nothing is overwritten silently (owner §79).** A NEW row is imported unless skipped. A CONFLICT is resolved KEEP_PLATFORM or SKIP; USE_OFFLINE, MERGE and NEW_VERSION are refused in BCP-1 because no wired command can apply them. UNSUPPORTED and INVALID rows must be skipped explicitly. Every explicit resolution carries a reason and is audited.
6. **The preview is a dry run of the real commands.** `api.preview_bcp_import` runs every row to import through its command, as the importer, inside a block that is always rolled back, and reports each row's outcome (OK or the command's own error code; any other error is reported as `CDF_ERROR`). References between rows (an allegation naming a subject row of the same workbook, or of an earlier import of it) resolve to the objects created for them. Referenced platform objects (a defence notice, a recommendation item) must belong to the workbook's case. Submission needs the importer's own preview hash, every row resolved and a clean dry run, repeated at submission.
7. **A different person approves; the importer applies.** The approver holds `BCP_IMPORT_APPROVE`, sees the case (and so everything the rows record), is not the importer and recorded none of the rows offline. The approval is bound to the submitted hash; rows and resolutions are immutable from submission. Only the importer applies, in one transaction, through the same commands; any failing row aborts the whole import (`BCP_ROW_FAILED:<row id>:<code>`) and the batch stays approved until cancelled.
8. **Provenance is never overwritten.** Each imported row writes `exchange.bcp_provenance`: case, workbook id, sheet, row id, object type and id, ORIGINAL_EVENT_AT, RECORDED_OFFLINE_BY, IMPORTED_AT, IMPORTED_BY, a hash of the row and the markers RECORDED_OFFLINE and IMPORTED_LATER. It is append-only, unique per case, workbook id and row id (which makes re-import idempotent), and readable only by those who can see the object it describes (an action's owner with the action, everyone else with the case). A command that takes an original time gets the workbook's value (a defence response's original submission date); every other object keeps its command's own time and the original time lives in its provenance row and audit event. Offline times are never rewritten as import times.
9. **Audit and notifications.** BCP_IMPORT_STAGED, BCP_IMPORT_ROW_RESOLVED, BCP_IMPORT_SUBMITTED, BCP_IMPORT_APPROVED, BCP_IMPORT_REJECTED, BCP_IMPORT_CANCELLED, one BCP_ROW_IMPORTED per row (with the original time, recorder and markers) and BCP_IMPORT_COMPLETED; each command also writes its own event. Audit metadata carries ids, codes and counts, never cell text. BCP_IMPORT_APPROVAL_REQUESTED goes to the eligible approvers and BCP_IMPORT_DECIDED to the importer (ids only, N18).
10. **Permissions are OWNER_DEFAULT (SOURCE_REQUIRED: "authorized continuity users").** `BCP_IMPORT`: Case Manager, Lead Investigator, GRC Director; each can import only what their own permissions allow, as the dry run shows. `BCP_IMPORT_APPROVE`: Case Manager, GRC Director. The Committee Secretary gets `BCP_IMPORT` with the committee-scoped workbook.

## Consequences

- An import does exactly what the importer could have done online, row by row, with the offline origin recorded; it grants nothing.
- A restricted case needs no extra consent to import: the importer and approver must both pass the restricted-case gate, and each command keeps its own restricted-case rules.
- The dry run spends no business number in BCP-1 (none of the four commands draws one), but leaves gaps in the audit ledger's sequence; the hash chain is unaffected.
- The uploaded file is not kept, only its SHA-256; the staged cells stay with the batch, including for rejected and cancelled batches, until a records policy says otherwise (SOURCE_REQUIRED). Production should keep the original workbook in the private evidence store as the source record (PRODUCTION_SUBSTITUTION_REQUIRED).
- Dates must be typed as ISO text (the template formats every column as text); Excel serial dates are refused rather than guessed.

## Production mapping

| Prototype                                 | Production (PRODUCTION_SUBSTITUTION_REQUIRED)                           |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `node:zlib` SpreadsheetML subset reader   | Vetted workbook reader in the CDF runtime, behind the same port         |
| Mock malware scanner on upload            | CDF malware scanning service                                            |
| Only the file hash kept                   | Original workbook kept in the private OSS evidence store, KMS-encrypted |
| Offline recorder named by synthetic email | CDF directory account                                                   |
