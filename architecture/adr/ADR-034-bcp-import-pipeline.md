# ADR-034: Continuity workbook template BCP-1 and the governed import pipeline

- **Status:** Proposed (2026-10-12). Linear CDF-197; the P12-6b-1 amendment CDF-258 (2026-10-18). Implemented in migration 1960 (local, pending security review). Security-sensitive.
- **Protocol:** §12, §19, §29, §45, §68, §82–§83, §87; ADR-027, ADR-021, ADR-023, ADR-024, ADR-033; owner Q&A Q100.

## Context

ADR-027 decides that a full outage is run from a governed Excel workbook and that its records come back through validation, a difference review, approval by a separate user and a transactional import through the same commands, with the offline provenance kept (Q100). It leaves open the template's exact shape, how a workbook is read safely, how rows map to commands, what a conflict is, who approves, and how the original event time survives an import that runs through commands which stamp their own time.

## Decision

1. **One versioned template, BCP-1.** The template is defined once, in `@cdf/contracts` (`BCP_TEMPLATE`), and seeded as reference data (`exchange.bcp_template_column`); a test keeps the two equal. It has the 27 sheets of the owner's list, 00_README to 26_IMPORT_AUDIT. Row 1 of a data sheet holds the column codes, row 2 their labels, and data starts on row 3. Every data row carries `ROW_ID` (a stable `BCP-` key or a UUID; never the Excel row number), `OBJECT_ID` (the platform object the row is about, if any), `ORIGINAL_EVENT_AT` and `RECORDED_OFFLINE_BY`. 01_CONTROL names the template version, the workbook id, the case (id and number, both required), the offline window and who prepared it. The empty template ships as `infrastructure/bcp/BCP-1_template.xlsx`, generated by `buildBcpTemplate` from that definition with bilingual column labels from `@cdf/i18n` (every cell formatted as text, header rows frozen); a unit test keeps the committed file byte-identical to the generator's output. Synthetic saves of it by openpyxl and LibreOffice Calc are reader test fixtures.
2. **BCP-1 imports four sheets of a case workbook; the others are recorded, not imported.** 05_SUBJECTS (`api.add_case_subject`), 06_ALLEGATIONS (`api.add_allegation`), 18_EMPLOYEE_NOTICE (a defence response received on paper, `api.record_defence_response`) and 21_CORRECTIVE_ACTIONS (`api.open_corrective_action`). Rows on every other sheet are staged as UNSUPPORTED and must be skipped explicitly; they are entered online after restoration. A case workbook belongs to the case team, who see the case. The committee's offline work (meetings, attendance, conflicts, votes, minutes and the authority decision the secretary records, CDF-159) needs a workbook scoped to a committee proceeding, because the secretary does not see the case (DEC-02, ADR-031); grievances need one scoped to the Grievance Committee. Those, documents and evidence (a companion package, after UX S2), status history and a pre-filled check-out workbook are the next increment.
3. **The workbook is untrusted input, read without a new dependency.** The reader (`readWorkbook` in `@cdf/infrastructure`, behind the `WorkbookReader` port) uses `node:zlib` only. It checks the compressed size, the entry count and every entry's declared size before inflating anything, inflates with a hard output limit and counts every byte it inflates against the total (a part read twice counts twice), refuses encrypted, ZIP64, unknown-method, duplicate, absolute and `..` entries, and parses only the workbook, its relationships, the shared strings and the worksheets those name, each part once: a sheet naming a part already read is refused, so one large part cannot be inflated and parsed once per sheet. It refuses any DTD or entity declaration, decodes only the predefined and numeric character references, and returns every cell as a string, flagging formula cells. It covers the subset of SpreadsheetML that the BCP-1 template and Excel or LibreOffice saves of it use; anything else is refused (PRODUCTION_SUBSTITUTION_REQUIRED: a vetted reader in the CDF runtime). The upload is scanned by the `MalwareScanner` port first, and only a CLEAN result is read. Caps (`BCP_WORKBOOK_LIMITS`): a 10 MiB file (`BCP_MAX_WORKBOOK_BYTES`, also checked by the application before the scan), 200 entries, 64 MiB per inflated entry, 128 MiB inflated in total, a compression ratio of 500, 40 sheets, 2 100 rows, 67 200 cells and 32 columns per sheet, 20 000 characters per cell, 268 800 shared strings and an XML nesting depth of 64. A refusal is a stable code with no file content: from the container NOT_A_ZIP, TOO_LARGE, MULTI_DISK, ZIP64, TOO_MANY_ENTRIES, ENCRYPTED, UNSUPPORTED_METHOD, UNSAFE_PATH, DUPLICATE_ENTRY, ENTRY_TOO_LARGE, TOTAL_TOO_LARGE, RATIO_TOO_HIGH, CORRUPT; from the XML DTD, ENTITY, MALFORMED, TOO_DEEP; from the workbook MACROS, EMBEDDED_CONTENT, EXTERNAL_LINK, NOT_A_WORKBOOK, UNSUPPORTED_SHEET, UNSUPPORTED_CELL, TOO_MANY_SHEETS, SHARED_PART, TOO_MANY_ROWS, TOO_MANY_CELLS, TOO_MANY_COLUMNS, CELL_TOO_LONG.
4. **Staging validates twice and classifies every row.** The application accepts only an `.xlsx` file uploaded from the case page its control row names (WORKBOOK_CASE_MISMATCH otherwise), checks the template (`readBcpWorkbook` in `@cdf/domain`: exactly the 27 sheets, row 1 the column codes from column A and typed, one typed control row on row 3, version BCP-1, no cells beyond a sheet's columns, at least one row) and validates the control row and rows with the same column rules as the database (`@cdf/validation`, §45; a database test keeps the two equal on every column kind); the database checks them again in `api.stage_bcp_import`. The importer (`BCP_IMPORT`) must see the case the control names (`NOT_FOUND` otherwise). Each row is NEW, CONFLICT (it names an existing object, or a row already imported from this workbook has changed), ALREADY_IMPORTED (no-op), UNSUPPORTED or INVALID (with the failing column). An event time must fall within the control's offline window, not before the case was created and not in the future; the workbook's preparer and each row's offline recorder must be ACTIVE platform users who can see the case now (a control naming anyone else is refused, a row is INVALID). The importer can tell from that whether a named person sees the case; the importing roles are those that see the full roster (DEC-08/10). One case and workbook id have at most one open batch.
5. **Nothing is overwritten silently (owner §79).** A NEW row is imported unless skipped. A CONFLICT is resolved KEEP_PLATFORM or SKIP; USE_OFFLINE, MERGE and NEW_VERSION are refused in BCP-1 because no wired command can apply them. UNSUPPORTED and INVALID rows must be skipped explicitly. Every explicit resolution carries a reason and is audited.
6. **The preview is a dry run of the real commands.** `api.preview_bcp_import` runs every row to import through its command, as the importer, inside a block that is always rolled back, and reports each row's outcome (OK or the command's own error code; any other error is reported as `CDF_ERROR`). References between rows (an allegation naming a subject row of the same workbook, or of an earlier import of it) resolve to the objects created for them. Referenced platform objects (a defence notice, a recommendation item) must belong to the workbook's case. Submission needs the importer's own preview hash, every row resolved and a clean dry run, repeated at submission.
7. **A different person approves; the importer applies.** The approver holds `BCP_IMPORT_APPROVE`, sees the case (and so everything the rows record), is neither the importer nor the workbook's preparer, and recorded none of the rows offline. The approval is bound to the submitted hash; rows and resolutions are immutable from submission. Only the importer applies, in one transaction, through the same commands; any failing row aborts the whole import (`BCP_ROW_FAILED:<row id>:<code>`) and the batch stays approved until cancelled.
8. **Provenance is never overwritten.** Each imported row writes `exchange.bcp_provenance`: case, workbook id, sheet, row id, object type and id, ORIGINAL_EVENT_AT, RECORDED_OFFLINE_BY, IMPORTED_AT, IMPORTED_BY, a hash of the row and the markers RECORDED_OFFLINE and IMPORTED_LATER. It is append-only, unique per case, workbook id and row id (which makes re-import idempotent), and readable only by those who can see the object it describes (an action's owner with the action, everyone else with the case). A command that takes an original time gets the workbook's value (a defence response's original submission date); every other object keeps its command's own time and the original time lives in its provenance row and audit event. Offline times are never rewritten as import times.
9. **Audit and notifications.** BCP_IMPORT_STAGED, BCP_IMPORT_ROW_RESOLVED, BCP_IMPORT_SUBMITTED, BCP_IMPORT_APPROVED, BCP_IMPORT_REJECTED, BCP_IMPORT_CANCELLED, one BCP_ROW_IMPORTED per row (with the original time, recorder and markers) and BCP_IMPORT_COMPLETED; each command also writes its own event. Audit metadata carries ids, codes and counts, never cell text. BCP_IMPORT_APPROVAL_REQUESTED goes to the eligible approvers and BCP_IMPORT_DECIDED to the importer (ids only, N18).
10. **Permissions are OWNER_DEFAULT (SOURCE_REQUIRED: "authorized continuity users").** `BCP_IMPORT`: Case Manager, Lead Investigator, GRC Director; each can import only what their own permissions allow, as the dry run shows. `BCP_IMPORT_APPROVE`: Case Manager, GRC Director. The Committee Secretary gets `BCP_IMPORT` with the committee-scoped workbook.

## Consequences

- An import does exactly what the importer could have done online, row by row, with the offline origin recorded; it grants nothing.
- A restricted case needs no extra consent to import: the importer and approver must both pass the restricted-case gate, and each command keeps its own restricted-case rules.
- The dry run spends no business number in BCP-1 (none of the four commands draws one), but leaves gaps in the audit ledger's sequence; the hash chain is unaffected.
- The uploaded file is not kept, only its SHA-256; the staged cells stay with the batch, including for rejected and cancelled batches, until a records policy says otherwise (SOURCE_REQUIRED). Production should keep the original workbook in the private evidence store as the source record (PRODUCTION_SUBSTITUTION_REQUIRED).
- Dates must be typed as ISO text (the template formats every column as text); Excel serial dates are refused rather than guessed.

## P12-6b-1 amendment: the continuity import's page (2026-10-18)

UX redesign Phase 12, slice P12-6b-1 (Linear CDF-258), with no migration: the page reads `api.bcp_import_batch_view`
as 2110 left it (ADR-047) and runs the batch commands. The coordinator's ruling of 2026-10-18 (12:18) settles the forks
of the P12-6b domain map. Who may read a batch and what each command accepts are unchanged. Each form shows only where
the view says its command would accept the caller now (UX-116), and runs its `api.*` command in the caller's security
context through the continuity import service, which validates with the shared schema and pre-checks the role
permission first (`BCP_IMPORT` to prepare, submit, import or cancel; `BCP_IMPORT_APPROVE` to decide); the database
decides again on submit, including that the importer is an authorized continuity operator (DEC-F30).

- **The page** (`/continuity/imports/{id}`). A staged batch is its importer's alone; once submitted, the approvers who
  see its case read it too. Anyone else, and an id that names nothing or a malformed one, get the same 404, with
  ACCESS_DENIED recorded. The page shows the workbook (its id, template, case, offline window, preparer and importer,
  the file's fingerprint) and its rows sheet by sheet as the view gives them: row metadata only, never a cell, the
  control sheet or a row about the reader. The row counts are counted over the rows the page lists, so they never tell
  the reader about a row the view leaves out. How long staged rows are kept is SOURCE_REQUIRED and says so (DEC-F31).
  A guide says where the import stands, who acts next and what the reader can do; a person is "you", the directory's
  name in the reader's language, or "a user". A workbook reported lost (AMB-205) and a batch changed since it was
  submitted are said in words; neither is ever approved or imported.
- **Preparing.** While the batch is staged, its importer skips a row with a reason (the only resolution this page
  offers, F4), runs the dry run, which undoes everything and shows each row's outcome in words (never the command's
  code), and submits the batch as the last clean dry run left it. Until then the page lists what holds the submission:
  rows that need a decision, a dry run of the batch as it stands, and rows the last dry run refused.
- **Deciding** (F13). An approver decides on what each row is and what will happen to it, exactly as submitted: the
  row metadata the view gives, never the cells. That is what 2110 built, and it satisfies §7 above: the approver sees
  the case, where the rows land, and showing the cells would widen access before 2160 (coordinator ruling). The
  workbook's preparer and anyone who recorded a row offline never decide, and find nothing of it in My Work.
- **Importing and cancelling.** Once approved, the importer imports every approved row at once, after a confirmation;
  if one row is refused, nothing is imported and the batch stays approved. The service answers that with one code,
  BCP_ROW_FAILED, and the row and its code stay on the server. The importer cancels an open batch with a reason.
- **A committee workbook** (ADR-047) is shown read-only: it goes on only through its official record (ADR-061), whose pages come later. Until it is imported or ends, the page names no one who acts next, and tells its importer that what comes next is on the record. The submission says it was submitted only when the command answers `SUBMITTED`: a committee record that does not reconcile answers otherwise (2115), and the page, read again, shows the batch as it stands.
- **My Work.** IMPORT_TO_APPROVE opens the batch's page, and `/continuity/imports` joins the live purpose roots.
- **Audit.** The commands record BCP_IMPORT_ROW_RESOLVED, BCP_IMPORT_PREVIEWED, BCP_IMPORT_SUBMITTED,
  BCP_IMPORT_APPROVED or BCP_IMPORT_REJECTED, one BCP_ROW_IMPORTED per row, BCP_IMPORT_COMPLETED and
  BCP_IMPORT_CANCELLED as before, with ids, codes and counts only. A refused command is recorded as COMMAND_DENIED with
  the command and outcome only.
- **Not in this change** (the P12-6b read-model migration, numbered at its turn): reporting a workbook lost (F2),
  uploading a workbook from the page (F3) and the template download it gates (F12), row resolutions other than skipping
  (F4) and lists of imports (F8). The continuity-operator registry's administration (DEC-12) goes to P12-10, with 2160
  (coordinator, 2026-10-18 12:27).
- **Tests.** Unit: the page's words for every status, row state, resolution, sheet, column, row detail, dry-run outcome
  and refusal in both languages, where the import stands and who a line names (`continuity/imports/labels.test.ts`); the
  gateway's view; the service's uniform not-found with ACCESS_DENIED and its one code for a failed row.
  `tests/e2e/continuity-imports.spec.ts` (+3): the importer skips the row that cannot be imported, runs the dry run and
  submits, the GRC Director approves from My Work and the importer imports the rows, which reach the case, in Arabic at
  390 px and English at 1280 px; a staged batch that its approvers may not read, a submitted one its preparer reads
  without deciding, an investigator, and the same 404 for an id that names nothing and a malformed one.
  `tests/accessibility/continuity-imports.spec.ts` (+4): the staged batch with its rows and the skip form, its error
  summary, the submission's confirmation after a clean dry run, and an approver's page with the approval's
  confirmation, at 1280, 390 and 320 px in both languages. The fixture's workbook id is the longest the template allows
  (64 characters): a workbook id and a row id wrap anywhere, so a phone never scrolls sideways.
