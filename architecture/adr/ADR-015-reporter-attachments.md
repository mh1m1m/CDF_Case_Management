# ADR-015: Reporter attachments via public_api

- **Status:** Proposed (2026-10-10). Needs the security thread's review (CDF-62 owner) before the PR leaves draft (CDF-72).
- **Protocol:** §22–§27, §29, §39, §40, §45, §46, §68, §83, §87; Drive whistleblowing requirements report, field 19; ADR-004, ADR-006; threats T02, T05, T10, T21

## Context

Field 19 of the Drive requirements report lets a reporter attach supporting documents in approved formats and sizes. CDF-63 (PR #22) aligned the rest of the form and shipped a notice that attachments are not available yet. The Phase 7 evidence pipeline (migration 0900, ADR-006) cannot be reused as it stands:

- `evidence.evidence.case_id` is NOT NULL, but most reports have no case yet.
- Its commands are `api.*`, which require an authenticated case-team member.
- It stores the original file name, which a reporter may have chosen to include their own name.

The portal has no session. It authenticates a reporter by Report ID plus HMAC(pepper, secret) (§23). It must never reveal whether a Report ID exists, and it must not store network metadata (T21).

## Decision

### Report-scoped attachments, same storage and allow-list as evidence

- New table `intake.report_attachment` belongs to one report.
  - **Columns:**
    - `report_id`;
    - `sequence_no`, giving the display name `ATT-001.pdf`;
    - `source`: `REPORT` for files added from the receipt, `FOLLOW_UP` for files added from the follow-up page;
    - `object_key`;
    - `file_extension`, `content_type`, `size_bytes`, `sha256`;
    - `status`: `QUARANTINED`, then `AVAILABLE` or `REJECTED`;
    - `scan_status`, `scanner`, `rejection_code`;
    - `received_at`, `stored_at`.
  - **The original file name is not stored anywhere.** Investigators see `ATT-001.pdf`. The reporter's file name can carry identity, so it never reaches the database, the audit trail or a log.
- Content types reuse `evidence.allowed_content_type` (an FK), so evidence and attachments share one allow-list.
- **Size limits:**
  - 4 MiB per file. This keeps a single upload request under the Vercel request-body limit.
  - At most 10 live (non-rejected) files and 20 MiB per report.
  - The same content cannot be attached twice to one report.
- Object keys are generated by the database: `reports/{report_id}/attachments/{attachment_id}`. Both UUIDs are random and the key is unique and immutable. The storage adapters accept only this pattern and the evidence pattern (T05).
- Objects use the existing private buckets `evidence-quarantine` and `evidence-vault` (migration 1000). There is no public bucket and no storage policy for any application role.
- **Immutability:**
  - Delete and truncate are rejected for every role, the owner included.
  - A row may change only while `QUARANTINED`, and only its outcome columns.
  - There is no delete command (records rule).

### Upload: public_api commands plus the storage and scanner ports

The portal server drives every upload, one file per request, in this order:

1. **Boundary checks.**
   - A route handler accepts `multipart/form-data` only from the same origin. It requires `Content-Length` and refuses bodies over 4 MiB + 64 KiB before reading them.
   - The application layer checks the file:
     - name sanitised, with bidi and format characters removed (CDF-68);
     - extension on the allow-list;
     - size within bounds;
     - the sniffed content type matches the extension; the browser-declared type is ignored.
   - Rate limits per hashed client key: **20 files per hour** (count) and **40 MiB per hour** (bytes, counted in KiB through the new `public_api.consume_rate_limit_amount`).
2. **`public_api.register_report_attachment(report_ref, secret_hmac, source, extension, content_type, size, sha256)`**
   - Credentials go through `public_api._authenticate_report`: the same lockout, the same `REPORT_ACCESS_FAILED` security event, and the same empty answer for a wrong secret and an unknown Report ID.
   - It re-validates every fact and enforces the per-report limits under a row lock.
   - It refuses closed reports.
   - It inserts the row `QUARANTINED` and writes `REPORT_ATTACHMENT_RECEIVED`, then returns the attachment id and object key.
3. `EvidenceStorage.putQuarantine` stores the object as an exclusive create, so it never overwrites.
4. `MalwareScanner.scan` runs. In the prototype this is `MockMalwareScanner`, which is **PRODUCTION_SUBSTITUTION_REQUIRED**.
5. The file is promoted to the vault and recorded with `public_api.complete_report_attachment` (`AVAILABLE`, audit `REPORT_ATTACHMENT_STORED`). Otherwise `public_api.reject_report_attachment` records it as `REJECTED`: audit `REPORT_ATTACHMENT_REJECTED`, plus a `MALWARE_DETECTED` security event when the reason is malware.

Both of those commands re-authenticate the report and act only on an attachment of that report. Every command writes its audit event in the same transaction:

- the actor type is `ANONYMOUS_REPORTER`;
- the metadata carries ids, codes, sizes and hashes only.

**Accepted trust boundary: the scan verdict.**

- The database cannot verify a scan. It trusts the `CLEAN` verdict that the portal server passes to `complete_report_attachment`.
- That server is the only anon database caller (login role `cdf_portal`); the browser never reaches the database.
- This is the same trust model as `api.complete_evidence_version`.
- What limits the impact: a table check enforces `AVAILABLE ⇒ CLEAN`, only `AVAILABLE` files can be downloaded, and downloads are served as sandboxed `nosniff` attachments.
- `MockMalwareScanner` is **PRODUCTION_SUBSTITUTION_REQUIRED**. In production the approved scanning service should sign or record its own verdict.

The byte limiter `public_api.consume_rate_limit_amount` accepts only the portal's `portal_attachment_kib:` bucket. A byte budget on any other bucket, such as a report's failed-access counter, could lock a known Report ID in one call.

### Download: scan gate first, then case visibility

- Investigators see attachments through RLS: `authz.can_view_report(report_id)`.
  - Once a case exists, that is `authz.can_view_case(case_id)`, the shared helper. It is never re-implemented here.
  - Before a case exists, the intake rule applies: `INTAKE_VIEW` plus clearance of at least the report classification.
  - `object_key` is not selectable.
- `api.open_report_attachment(id)` returns storage facts only for an attachment that meets all of these:
  - it is `AVAILABLE`, meaning it has passed the scan;
  - the caller can view the report;
  - the caller holds `EVIDENCE_DOWNLOAD`, or `INTAKE_VIEW` while there is no case.
- A successful open writes `REPORT_ATTACHMENT_DOWNLOADED`. Anything else writes a `REPORT_ATTACHMENT_ACCESS_DENIED` security event and returns nothing, so missing, hidden and quarantined files all look the same (§40).
- The investigation app streams the vault object with `attachment` disposition, `nosniff`, `no-store` and a sandboxing CSP, exactly like evidence.
- Investigators never see reporter identity. Attachments carry no vault data, and the display name is generated.

### What the reporter sees

- After submitting, the receipt offers an optional "Add supporting files" control. It uses the Report ID and secret that were just issued, and it holds them only in memory.
- The follow-up page offers the same control while the report is open.
- The reporter sees a per-file outcome: received, not accepted, or limit reached. Notifications carry no content (§39), and none are sent for attachments.
- The form tells reporters that files can contain hidden details, such as author names or photo location. It asks them to remove those details if they want to stay anonymous.

### Storage credential for the public portal (decision pending with the owner)

- The portal never holds the Supabase service-role key.
- The portal's storage port is used only to write, through `putQuarantine` and `promoteToVault`. It never opens a read stream.
- Attachments run with the local filesystem adapter in local and test environments (development, CI, e2e).
- On Vercel and hosted Supabase the upload control stays hidden (`CDF_PORTAL_ATTACHMENTS=off`, the default outside local/test) until the owner picks a storage-only credential.
- Production uses an Alibaba OSS RAM policy allowing `PutObject`/`CopyObject` on the `reports/` prefix only (**PRODUCTION_SUBSTITUTION_REQUIRED**).

## Consequences

- The intake team can review supporting files before a case is opened. Case visibility then governs them, with no copy step.
- **Carry-over into case evidence:**
  - Today an investigator who needs a file in the evidence register downloads it and registers it as evidence, which starts a custody chain.
  - Automatic carry-over with custody is a follow-up.
  - The default not taken is copying files at case creation. That would duplicate objects and blur custody.
- **Records:**
  - Attachments follow the report's public status: no uploads once it reads `CLOSED`, which includes closed and archived cases.
  - Once records retention (#14) lands, the 1300s `records.case_content_writable` rule should also gate `register_report_attachment` (follow-up).
- **Files are not sanitised.**
  - Hidden metadata (EXIF GPS, document author) is kept as uploaded. The reporter is warned.
  - Content disarm and metadata stripping is **PRODUCTION_SUBSTITUTION_REQUIRED** (the CDF-approved scanning service).
- One request per file adds round trips but keeps every request small and individually rate-limited.

## Production mapping

| Prototype                                                     | Production                                                                         |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Local filesystem storage (local/test); disabled on Vercel     | Alibaba OSS private buckets, WORM retention, KMS encryption, write-only RAM policy |
| `MockMalwareScanner` (EICAR only)                             | CDF-approved malware scanning and content-disarm service                           |
| PostgreSQL fixed-window limiter (`consume_rate_limit_amount`) | Edge WAF / API gateway limits by count and bytes                                   |
