## 5. Running the suites against hosted DEV (after CDF-32)

The database specs are target-agnostic: `tests/support/db.ts` connects with `CDF_BFF_DATABASE_URL`, `CDF_PORTAL_DATABASE_URL` and `CDF_ADMIN_DATABASE_URL` (or `CDF_TEST_DB_HOST`/`PORT`/`NAME` plus the login passwords). To run them against `cdf-case-dev`:

1. Apply migrations and the synthetic seed from Git (CDF-32); never seed by hand.
2. Run from a GitHub Actions job with the connection strings as masked secrets, never from a laptop and never committed.
3. `pnpm test:security` runs everything in one rolled-back transaction per scenario, except where a test says it commits synthetic data (portal and integration tests). Run `pnpm test:db` only on DEV, never on DEMO.
4. `CDF_ADMIN_DATABASE_URL` is used only for catalog inspection and assertions (owner connection). On Supabase use the `postgres` role through the session pooler.
5. For the bundle and HTML scan, run `node scripts/security/scan-client-bundles.mjs` after each Vercel build with that environment's server secrets present in the build environment; the e2e specs run against preview URLs once `APP`/`PORTAL` in `tests/e2e/support.ts` are made configurable (CDF-33).
