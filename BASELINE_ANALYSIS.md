| ------------------------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| 19 WB-FRM form definitions (184 fields)                      | **MIGRATE**                                               | Core business knowledge. Becomes `form_definition` / `form_field_definition` seed data plus typed Zod schemas, keyed by Case_ID                              |
| Workflow stage names and order                               | **REFACTOR**                                              | Mapped onto the protocol's 15 baseline states (section 31) with explicit transition definitions instead of "next form" progression                           |

## 2. Current repository map (baseline)

There was no repository. The baseline is a deployable artefact, not a source tree:

```
CDF_Case_Platform_Local_Package.zip
├── CDF_Case_Platform.html          ← everything: CSS, 3 scripts, 5 images, 19 forms, all views
│   ├── <script id="cdf-brand-preboot">     theme/language before paint
│   ├── <script>                            application (CFG, data layer, views, enterprise RBAC overlay)
│   │     ├── CFG.FORM_DATA / WORKFLOW / SOURCES / EMAIL_TEMPLATES / DEFAULT_CONFIG
│   │     ├── IndexedDB wrapper (put/get/all/del), logEvent(), upsert(), applyEvent()
│   │     ├── legacy views (v4) …
│   │     └── "enterprise" overlay (v5) that monkey-patches the legacy functions
│   └── <script id="cdf-brand-i18n-runtime">   Arabic→English DOM replacement
├── CDF_Local_Server.ps1
├── Start_CDF_Platform.cmd
└── README_CDF_Local_Launcher_AR.txt
```

### Current architecture

```
Browser (Edge/Chrome, one device)
 └── CDF_Case_Platform.html
       ├── UI (innerHTML templates)
       ├── "authorization" (JS functions in the same page)
       ├── identity (self-asserted local profiles; dropdown to switch user)
       └── IndexedDB (all data, including evidence files and reporter identities)
             └── optional: JSON events copied to a Nextcloud-synced folder
```

There is no server, no network boundary, no authentication and no database outside the browser.

### 5.2 Structural weaknesses in the baseline model

1. **No referential integrity.** Every relationship is a string id that may dangle; deleting a case leaves orphan forms and evidence.
2. **Sequential, guessable business numbers as the only lookup in several places** (`TKT-YYYY-NNNNN`, `CASE-YYYY-NNNN`, computed as `count + 1`, which also collides after deletes or concurrent devices).
3. **Free-text people.** Prepared/reviewed/approved-by, investigators in WB-FRM-10, committee members in WB-FRM-13 are typed names, not user references, so accountability cannot be proven.
4. **Duplicated case data.** WB-FRM-01 re-captures subject, category, dates already on the ticket and case.
5. **Classification as Arabic display strings** (`مقيد`, `سري - عند اعتماده`), so policy cannot be evaluated by machine.
6. **No version history** for cases, forms, evidence or documents; `upsert` overwrites and increments a counter.
7. **Workflow state equals "next incomplete form"**, so the state can move backward or skip when forms are edited.

## 6. Security gap analysis

Ranked by impact. Each item names the baseline behaviour and the target control.

| #   | Weakness in baseline                                                                                                                                                                                                                                                                | Impact                                       | Target control                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | **All authorization runs in the browser** next to the data. Anyone with the device can open DevTools and read every IndexedDB store, including the reporter vault and evidence files                                                                                                | Total confidentiality loss                   | Server-side BFF + PostgreSQL RLS (default deny); browser never holds data it is not entitled to                                                             |
| S2  | **Self-asserted identity.** Profiles are created locally; the first profile becomes platform admin; a dropdown switches between users (`DEVELOPMENT_IDENTITY_MODE`)                                                                                                                 | No authentication, no accountability         | Supabase Auth (prototype) behind `IdentityProvider`, future CDF OIDC IdP                                                                                    |
| S3  | **Reporter identity leaks into the audit log.** The legacy `upsert()` writes the full record into `events.payload`, so `REPORTER_VAULT_CREATED` events carry name, ID number and mobile                                                                                             | Whistleblower exposure through audit exports | Vault rows never pass through generic audit payloads; audit stores references only                                                                          |
| S4  | **Identity shown on page load** to any holder of `REPORTER_IDENTITY_VIEW`, without justification or approval; the log entry is written after display                                                                                                                                | Uncontrolled reveal                          | `resolve_reporter_identity()` requiring permission, case access, justification, optional approval, and an audit event in the same transaction               |
| S5  | **Audit log is mutable.** The same page can `put`/`del` events; restoring a backup replaces history; signatures use keys stored beside the data                                                                                                                                     | Tampering undetectable                       | DB append-only table, no UPDATE/DELETE privilege for any application role, triggers that reject modification, DB-computed hash chain, verification function |
| S6  | **Evidence can be overwritten or deleted** (`put`, `del`); no versions; extension deny-list only; files stored with user filenames                                                                                                                                                  | Integrity and chain-of-custody failure       | Private buckets, random object keys, version-per-upload, quarantine → validation → vault, MIME sniffing, size limits, malware-scanner adapter               |
| S7  | **Unguarded legacy paths.** The v4 case search scans `JSON.stringify` of every case. In v5 the enterprise overlay shadows these functions by reassignment instead of removing them, so filtering depends on which wrapper is called, and every record is still loaded into the page | Case enumeration                             | Authorization applied in SQL before results are produced; no unfiltered query paths                                                                         |
| S8  | **Raw error messages rendered** (`e.message` into HTML)                                                                                                                                                                                                                             | Information disclosure                       | Standard safe errors with correlation IDs                                                                                                                   |
| S9  | **PowerShell launcher uses `-ExecutionPolicy Bypass`**                                                                                                                                                                                                                              | Weakens endpoint policy                      | Not needed in hosted model                                                                                                                                  |
| S10 | **Conflict of interest does not remove access**, only voting                                                                                                                                                                                                                        | Conflicted users keep reading the case       | Declared conflict denies access in RLS                                                                                                                      |
| S11 | **No classification enforcement**; classification is a label                                                                                                                                                                                                                        | Over-sharing of sensitive cases              | Machine-readable classification + clearance and restricted-case ABAC in RLS                                                                                 |
| S12 | **Exports have no approval or record**                                                                                                                                                                                                                                              | Mass exfiltration                            | Export as a domain operation with approval for high sensitivity, watermark and audit                                                                        |
| S13 | **Sequential business ids as lookups**                                                                                                                                                                                                                                              | IDOR / enumeration when combined with S1/S7  | UUID primary keys; authorization on every lookup; non-sequential public report references                                                                   |
| S14 | **Sync replays events from a shared folder** after hash/signature checks against keys that are themselves in the synced data                                                                                                                                                        | Injected records                             | Not ported                                                                                                                                                  |

Positive security work in the baseline worth keeping: default-deny intent, "platform admin gets no case content", time-bounded scoped grants, recusal on conflict, SOURCE_REQUIRED instead of invented governance values, content-free notification wording, hash chaining as a concept, and redacted export as a concept.

## 8. Migration plan

### 8.1 Principles

1. Nothing from the baseline runs in the new platform; knowledge is migrated, code is not.
2. Business knowledge moves as **seed data and typed definitions** (forms, workflow, roles, templates), reviewed in PRs.
3. Every schema element arrives through a numbered migration (section 13).
4. There is no data migration: the baseline ships no records, and the target holds synthetic data only (section 2).

### 8.3 Baseline features intentionally not carried forward

| Feature                                | Why                                                                                          | Replacement                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Offline-first single device operation  | Conflicts with central authoritative database and server-enforced security                   | Hosted apps; offline is out of scope for the reference implementation |
| Nextcloud folder sync                  | Replaced by central DB; synced folders would duplicate sensitive data outside access control | None                                                                  |
| Local passphrase lock                  | Not encryption; replaced by authenticated sessions with idle timeout                         | Session management                                                    |
| Per-user browser ECDSA signatures      | Keys stored with the data                                                                    | `KeyManagementProvider` (future KMS/HSM signing)                      |
| Encrypted JSON backup/restore by users | Users restoring history defeats the audit model                                              | Managed DB backups (BCDR mapping)                                     |
| In-page certification panel            | Self-certification; replaced by CI evidence                                                  | `compliance/` + CI artefacts                                          |

None of these is a loss of a governed business capability; each is an infrastructure workaround for having no server.

### 8.4 Archive handling

The original ZIP and HTML are kept outside Git (they embed ~430 KB of images and add nothing the extraction does not). Their SHA-256 values are recorded in section 1.1 and in [`baseline/ARCHIVE_MANIFEST.md`](baseline/ARCHIVE_MANIFEST.md) so the extraction can be verified against the originals. The originals remain in the project's shared files.
